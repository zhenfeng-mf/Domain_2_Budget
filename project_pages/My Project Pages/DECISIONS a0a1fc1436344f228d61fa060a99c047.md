| D-02 | 2026-09-08 | Money is stored as integer yen everywhere — columns, forms, calculations, display | Decimal or float columns | JPY has no minor unit, so integers remove rounding risk entirely. Tradeoff: none meaningful for this domain; would need revisiting only for multi-currency. |  |
| D-01 | 2026-09-08 | `rails new . -d mysql` — Rails 8 + MySQL, Minitest, Rails 8 default asset pipeline, generated in place | RSpec; `--css=tailwind` at init; a separate app subdirectory | Framework defaults minimize setup and maintenance cost against a 64h budget, and "the default was sufficient" is defensible. CSS left open so it is added only if the UI needs it. |  |
| D-03 | 2026-09-08 | `used_on` is a `date` column, not a datetime | `datetime` | 利用日 is a calendar day. A timestamp introduces timezone-dependent month attribution — the easiest silent bug in this domain. |  |
| D-04 | 2026-09-09 | Approved used amount is **stored**: `budgets.approved_total` (int yen), written only by `ApproveExpense`, guarded by `CHECK (approved_total <= amount)` | Deriving it on read with `SUM(expenses.amount)` where status = 承認済み | A DB `CHECK` cannot aggregate across rows, so a derived total can only ever be protected by application code. Storing it puts the guarantee in MySQL: the row physically cannot exist in an overspent state, even from the console. Cost accepted: a denormalised value that can drift. Drift is bounded because 承認済み is terminal (A-02) so the counter only grows, exactly one service writes it, and a reconciliation test asserts `approved_total == approved_sum`. | ⭐ |
| D-05 | 2026-09-09 | Cap enforced in two layers: `ApproveExpense` runs one transaction that takes `SELECT … FOR UPDATE` on the expense then the budget, re-reads the total after the lock, and refuses; the DB `CHECK` is the backstop | Lock-only with a derived `SUM`; optimistic locking with retry | Lock-only is correct today but the correctness lives in Ruby, so one future path that forgets the lock breaks the invariant silently. `CHECK`-only cannot serialise the read-modify-write. Together the lock produces a correct, readable refusal and the constraint makes overspend impossible. Cost: approvals against one budget serialise (fine — one approver, low volume), and a fixed lock order expense → budget is now a rule the codebase must keep or concurrent approvals deadlock instead of queueing. Proof: `test/models/concurrent_approval_test.rb`, two threads on one ¥10,000 budget with two ¥6,000 expenses — exactly one wins. | ⭐ |
| D-06 | 2026-09-08 | Add Tailwind CSS via `tailwindcss-rails`, rather than hand-writing plain CSS | Plain CSS in `application.css`; a component framework such as Bootstrap | Utility classes keep styling co-located with the ERB that uses it, so there is no parallel stylesheet to keep consistent as screens are added. Bootstrap was rejected because its opinionated components are harder to bend to a dense approver queue. Tradeoff accepted: an extra build step, so `bin/dev` is now the way to run locally and CI must build CSS before asset-dependent tests. |  |
| D-07 | 2026-09-09 | Two Dockerfiles: the generated multi-stage `Dockerfile` for production, `Dockerfile.dev` for compose | One single-stage image used for both | The dev image optimises for iteration (volume mount, CSS watcher); the prod image optimises for size and runs non-root. Cost: two files to keep in sync, and the Tailwind build step has to be proven separately in the prod image. |  |
| D-08 | 2026-09-09 | `budgets.year_month` is a `date` column pinned to the 1st of the month, with `CHECK (DAYOFMONTH(year_month) = 1)` | String `"2026-09"`; integer `202609`; deriving the month from `used_on` with no column at all | A real date sorts, compares and does month arithmetic without parsing, and it indexes cleanly in the I-02 composite unique index. Pinning to the 1st means one canonical bucket value, produced by the single `MonthBucket.for` method that I-07 depends on. Cost: the pinning is only true because a `CHECK` enforces it — without that, a mid-month value would silently create a second bucket. Resolves Q-08. |  |
| D-09 | 2026-09-09 | Authentication is `has_secure_password`  • bcrypt with `session[:user_id]`, in a small `Authentication` controller concern | Devise; Rails 8's `bin/rails generate authentication` | Signup / login / logout is roughly 60 lines here, and REQUIREMENTS §7 already puts real authentication out of scope — the graded value is the budget invariant, so auth should consume as little of 64h as possible. The Rails 8 generator was rejected because it brings a `Session` model and password-reset mailers that collide with the `User` already designed. Cost: no password reset, lockout or rate limiting; stated in §10 out of scope. |  |
| D-10 | 2026-09-09 | `Team` exists in the schema from the first migration — `users.team_id` and `budgets.team_id`, with I-02 becoming `unique (team_id, year_month, category_id)` — but there is no team CRUD UI; teams come from seeds | A single global approver now, adding teams after the freeze if time allowed | A-05 makes the team the owner of a budget, so without `team_id` every team in the company would share one 2026-09 交通費 budget. Carrying the column now costs one migration; retrofitting it later would touch the unique index, every authorization check, the approve service and every test — after the Day 6 freeze that is not affordable. Cost: one model with no UI. Sub-decision: `teams.approver_id` is nullable at the DB because `users.team_id` is `NOT NULL` and MySQL has no deferrable constraints, so a mutual `NOT NULL` pair could never be inserted; presence is enforced in the app on update and by `Budget` refusing a team with no approver. Resolves Q-07. |  |
| D-12 | 2026-09-09 | Re-cut Days 3–6 into **vertical slices**: from here on, no business logic is written unless a route and screen exercise it in the same session | Continuing model-first — finishing all validations, services and model tests, then building controllers and views on top | Day 2 produced `ApproveExpense`, `RejectExpense`, the `approved_total` write path, the concurrency test and the I-08 / I-10 / I-11 validations with no route reaching any of them, so the app is only demoable up to login. Phase 4 of the process flow is explicit that slices must stay end-to-end. The deeper cost was feedback latency: 8h of code with zero executions. Kept as-is: the migrations, DB constraints and constraint tests (Phase 2/3 output — a table cannot be half-built), and the auth slice, which is Phase 4 slice 1 and does have screens. Not unwound: `approved_total` stays in the first migration per D-04, because re-cutting migrations per slice would churn the unique index and every test for no gain. Cost accepted: the Day 2 services sit unused for a day, which is sunk. Benefit: slice 6 (approve, where the assignment is won) now lands on Day 4 rather than Day 5. | ⭐ |
