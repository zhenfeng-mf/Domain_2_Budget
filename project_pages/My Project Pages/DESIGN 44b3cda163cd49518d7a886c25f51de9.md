## 1. Domain model

**The central split:** `Budget` is a *cap* owned by the approver. `Expense` is a *claim* against that cap, owned by the member. Different lifecycles, different owners, different screens — so they are separate models, not one table with a flag.

| Model | Key columns | Relationships | States |
| --- | --- | --- | --- |
| `Team` | `name`, `approver_id` (nullable at DB — see D-10) | belongs_to :approver (User), has_many :members, :budgets | — |
| `User` | `name`, `email`, `password_digest`, `role` (member / approver), `team_id` | belongs_to :team, has_many :expenses | — |
| `Category` | `name` | has_many :budgets, :expenses | — |
| `Budget` | `team_id`, `year_month` (date, 1st of month), `amount` (int yen), `approved_total` (int yen, D-04) | belongs_to :team, :category | — |
| `Expense` | `used_on` (date), `amount` (int yen), `purpose`, `status`, `submitted_at`, `decided_at`, `decided_by_id` | belongs_to :user, :category | 下書き / 申請済み / 承認済み / 却下 |

**Scope correction (D-10):** `Budget` belongs to a **team**, not to the whole company. A-05 says a team has one approver and many members, so a budget without `team_id` would be shared by every team — I-02 is therefore `unique (team_id, year_month, category_id)`.

### Settled design choices

- **Money is integer yen.** Never float or decimal. JPY has no minor unit, so integers remove rounding risk entirely.
- **`used_on` is a `date`, not a datetime.** 利用日 is a calendar day; a timestamp invites timezone-driven month-boundary bugs.
- **Month bucketing lives in exactly one method.** A month-boundary bug is the easiest silent failure in this domain.
- **Rejection is a state, never a delete.** Traceability matters in a money product.

| I-08 | **利用日 is immutable once the expense leaves 下書き** | validation on `used_on_changed?` unless `status_was` is draft | *not expressible — a `CHECK` cannot see the previous row value; a trigger would force `schema_format = :sql`* | 🚧 test written |
| I-09 | **Budgets are adjustable for future months only**, and no past-month budget can be created | validation on `amount_changed?` against `MonthBucket.current` | *not expressible — a `CHECK` cannot reference "now"* | 🚧 test written |
| I-10 | A non-draft expense always has a matching (team, month, category) budget — A-03 | validation on every non-draft save, so editing a 申請済み expense's category re-checks it | *not expressible across rows* | 🚧 test written |
| I-11 | 承認済み / 却下 are immutable — protects `approved_total` from drift | validation refusing any change when `status_was` is terminal | enum column | 🚧 test written |

## 4. The hard problem — concurrent approval against a cap

<aside>
🔑

Two approvers approve two different expenses against the same budget at the same moment. Each individually fits inside the remaining amount, but together they exceed it. Both `SUM` queries read the old total, both pass validation, and the budget is overspent.

A unique index cannot express "the sum of these rows must stay under a limit" — so this requires a real architectural choice.

</aside>

**Option 1 — pessimistic row lock.** In the approve transaction, `budget.lock!` first, recompute the approved `SUM`, then approve.

- ➕ The invariant lives in one readable place; nothing can drift
- ➖ Serializes all approvals for a given budget

**Option 2 — cached counter + DB check constraint.** Keep `approved_total` on `Budget`, update it in the same transaction, add `CHECK (approved_total <= amount)`.

- ➕ The database itself refuses to be overspent — the strongest possible guarantee
- ➖ A denormalized value that drifts if any code path forgets to update it; needs a reconciliation story

**Chosen: Option 2, with Option 1's lock kept** (D-04 + D-05). `approved_total` lives on `Budget` with `CHECK (approved_total <= amount)`, and `ApproveExpense` still locks — expense first, then budget — and re-reads the total after the lock.

**Why not lock-only:** it is correct, but the guarantee lives in application code, so one future path that approves without the lock breaks the invariant silently and nothing catches it. **Why not CHECK-only:** a constraint cannot serialise a read-modify-write, and a bare constraint violation is a poor error message for an approver. The lock makes approval correct and legible; the constraint makes overspend impossible even from the console.

**Accepted cost:** a denormalised counter that could drift, and serialised approvals per budget. Drift is bounded by I-11 (terminal states are immutable), by one service owning the write, and by `Budget#approved_sum` plus a reconciliation assertion in the tests.

**Lock order rule:** always expense → budget. Reversing it anywhere turns concurrent approvals into deadlocks.

> Validation alone has a race condition, so I moved the guarantee to where it cannot be bypassed.
>
