## Phase 1 — Requirements analysis (do NOT skip to coding)

This is the criterion 要件をシステム設計へ落とし込む力.

1. **Restate the requirements in your own words**, then list what is ambiguous. For the budget & expense app:
    - Which date drives the budget month — the 利用日 or the submission date? (Spec says 利用日.) What if a member changes the 利用日 to a different month while it is still a draft?
    - Can a member edit a 申請済み expense, or only withdraw it back to 下書き?
    - Is 却下 terminal, or can a rejected expense be edited and resubmitted?
    - What happens if no budget exists for the month + category of an expense? Can it even be submitted?
    - Can an approver approve their own expense?
    - Is there one approver for everything, or an approver per team? Is there one team or many?
    - Does lowering a budget need to warn about, or block on, already-approved spend? (Spec blocks below the approved total — what is the error UX?)
2. **Write down your assumption + rationale for each ambiguity.** "I found an ambiguity, here is how I decided, here is the tradeoff" is far stronger than silently picking one.
3. **Define the actors** and what each is trying to achieve. Two roles minimum (メンバー / 承認者). The approver is the one under time pressure — design for their queue, not just the submission form.
4. **Define the core value loop in one sentence**, and name the value moment.
    
    > An approver can open one screen, see the true remaining budget, and approve or reject in seconds — confident that the team can never overspend the budget, even by accident.
    > 

**Output:** `REQUIREMENTS.md` — restated requirements, assumptions table, actor definitions, explicit out-of-scope list.

## Phase 2 — Domain modeling & design

Most of the evaluation weight sits here.

### 2.1 Model the domain, not the UI wording

- **Separate the budget from the expense.** `Budget` (owned by the approver, one per month + category) and `Expense` (owned by the member) are different concepts with different lifecycles. The budget is the *cap*; the expense is a *claim* against it.
- **Money is integer yen.** Never float or decimal. JPY has no minor unit, so integers remove rounding risk entirely — and it is a one-line decision you can defend instantly.
- **The budget month is derived from the 利用日, not from “now”.** Store the usage date, then decide whether to denormalize a `year_month` column for indexing. Either choice is fine if you can justify it.
- **Expenses have a state machine, not a boolean.** `下書き → 申請済み → 承認済み | 却下`. Never delete to represent rejection. State transition rules are explicitly a scoring criterion.
- **Decide where the “approved used amount” lives.** Derived with `SUM` on read, or a cached counter column on `Budget`? This single choice drives your entire concurrency story — see §2.4.

### 2.2 Design the invariants

Conditions that must *always* hold:

- Exactly one budget per (month, category) → needs a **DB unique index**, not just a validation
- **Approved total for a (month, category) never exceeds its budget** → the hard one; it is a *sum across rows*
- Expense amount is an integer ≥ 1
- Budget amount ≥ 0, and can never be lowered below the already-approved total
- Only a 申請済み expense can be approved or rejected, and only once
- A member can edit or delete only their own 下書き
- Only 承認済み expenses count toward the used amount
- An expense is charged to the month containing its 利用日

### 2.3 Decide the enforcement layer for each rule

| Business rule | App layer | DB layer |
| --- | --- | --- |
| One budget per month + category | validation + rescue on unique violation | unique index on `(year_month, category_id)` |
| Approved total ≤ budget | approve service inside a transaction, `budget.lock!`, then re-check the sum | not expressible as a plain check constraint (sum across rows) — **either** cached counter + `CHECK (approved_total <= amount)` **or** the row lock. Document which and why |
| Amount is an integer ≥ 1 | numericality validation, integer column | unsigned int + `CHECK (amount >= 1)` |
| Budget ≥ approved total | validation comparing the current sum, inside the transaction | `CHECK (amount >= 0)` |
| Approve/reject once, only from 申請済み | state guard inside the transaction | enum column, optional check constraint |
| Expense belongs to a real member and category | FK + service object | foreign keys, NOT NULL |
| Only the owner can edit their draft | authorization policy in the controller | — |

### 2.4 Think about concurrency explicitly

Two approvers approve two different expenses against the same budget at the same moment, each individually fitting inside the remaining amount but together exceeding it. Both `SUM` queries read the old total, both pass validation, and the budget is overspent.

<aside>
🔑

This is **harder than a double-booking check**, and that is good news for your presentation. A unique index cannot express “the sum of these rows must stay under a limit,” so you have to make a real architectural choice.

</aside>

**Option 1 — Pessimistic row lock.** In the approve transaction, `budget.lock!` first, recompute the approved `SUM`, then approve.

- ➕ The invariant lives in one readable place; nothing can drift
- ➖ Serializes all approvals for a given budget

**Option 2 — Cached counter + DB check constraint.** Keep `approved_total` on `Budget`, update it in the same transaction, and add `CHECK (approved_total <= amount)`.

- ➕ The database itself refuses to be overspent — the strongest possible guarantee
- ➖ A denormalized value that can drift if any code path forgets to update it; needs a reconciliation story

Pick one, implement it, and be able to argue the other side. **Then write the test that proves it** — two concurrent approvals, and the total must never exceed the budget.

> Validation alone has a race condition, so I moved the guarantee to where it cannot be bypassed.
> 

### 2.5 Remaining design decisions

- **Dates & month attribution:** 利用日 is a calendar date, not a timestamp — use a `date` column. Use `Time.zone.today`, never `Date.today`. Put month-bucketing logic in *one* place; a month-boundary bug is the easiest silent failure in this domain.
- **Money:** integer yen everywhere — columns, forms, calculations, display formatting.
- **Authorization:** lives server-side, per action, tested. Views only hide things; controllers/policies prevent them.
- **Screens & flows:** sketch including empty states, error states, and confirmation states. Error guidance and clarity of completion state are evaluated UX.

**Output:** `DESIGN.md` with ER diagram, invariant/enforcement table, state transition diagram, screen flow sketch. Log rejected alternatives.

## Phase 4 — Build in vertical slices

Do not build all models, then all controllers. Build thin end-to-end slices so the app is always demoable.

1. Signup / login / logout — as simple as the spec allows; do not gold-plate auth if it is not required
2. Approver sets a budget for a month + category
3. Member creates an expense draft (利用日, category, amount, purpose)
4. Member submits the draft → status is visibly 申請済み
5. Approver sees the pending queue, **with remaining budget shown next to each request**
6. Approver approves → remaining budget updates *(first complete value loop — the cap invariant lives here)*
7. Approver rejects
8. Budget summary screen: budget / approved used / remaining per month + category *(a required feature — do not leave it to the end)*
9. Member views their own requests and current states

<aside>
⚠️

Slices 5 and 6 are where the whole assignment is won or lost. Get to them early, then spend real time on them.

</aside>

After each slice, ask: does it work, is it authorized, is the error path handled, is there a test?

## Phase 5 — Harden business rules & boundary conditions

Deliberately attack your own app:

- [ ]  **Approve two expenses concurrently** that individually fit but together exceed the budget (two browsers)
- [ ]  Approve an expense that exactly hits the budget, then approve one more yen
- [ ]  Approve an already-approved expense; reject an already-approved one
- [ ]  Approve a 下書き that was never submitted
- [ ]  Amount of 0, negative, `100.5`, a huge number, empty, or non-numeric
- [ ]  Edit or delete another member's draft by editing the URL/ID (**IDOR** — reviewers will test this)
- [ ]  Submit an expense whose month + category has no budget at all
- [ ]  Change a draft's 利用日 to a different month, then submit
- [ ]  Expense on a month boundary — last day and first day
- [ ]  Lower a budget below the already-approved total
- [ ]  Create a second budget for a month + category that already has one
- [ ]  Submit the same draft twice (double-click, then browser back button)
- [ ]  Submit the form with JS disabled / bypass client-side validation
- [ ]  Zero, one, and many pending requests

> Every hole you find and fix becomes a talking point. Every hole you do not find becomes a question you cannot answer.
> 

## Phase 6 — Tests that demonstrate judgment

Not about volume — about **which risks you identified and why you chose those cases**.

- **Model/unit tests** for every invariant, including the DB-level ones (assert the unique index and check constraints actually raise)
- **A concurrency test** for the budget cap — two simultaneous approvals must never overspend. Highest-value test in the project
- **Authorization tests**: member A cannot touch member B's draft; a member cannot set budgets or approve
- **State transition tests**: cannot approve a 下書き, cannot approve twice, cannot reject an approved expense
- **Boundary tests**: amount of exactly 1; approval that exactly hits the budget; one yen over; month-boundary 利用日; lowering a budget to exactly the approved total
- **One or two request/system tests** covering the happy path end to end

Then write `TESTING.md`: *"the 5 things that must never break, and how each is tested."* That document earns the point more than the test count.

## Phase 7 — Extras: pick few, justify hard

Where candidates most often lose rather than gain points. Extras must tie to a **user problem**, with an explanation of priority.

<aside>
✂️

Choose 2–3 extras done deeply over 8 shallow ones.

</aside>

| Extra | Why it scores well |
| --- | --- |
| **差し戻し** — send back to 下書き with a comment | The strongest pick. Approvers need a middle option between approve and reject; adds one state transition and a real user need you can articulate |
| Approval history / audit log | Who approved what, when, and at what remaining balance. Accuracy and traceability — very Money Forward |
| Over-budget warning *before* submitting | Stops the member wasting an approval cycle; shows you designed for both actors |
| Receipt attachment | Evidence and trust; file upload is a genuine engineering surface |
| Month-end summary or CSV export | A real operator need the spec hints at |
| Category management for the approver | Small, but makes the app feel like a product rather than a test |

Also prepare a **"consciously did NOT build"** list with reasons.

> I dropped multi-level approval chains because they multiplied the state machine for a scenario a small team does not have. Single-approver keeps the budget invariant provable.
> 

Hold a **feature freeze** with real time left. A polished smaller thing beats a half-broken bigger thing.

## Phase 8 — UX, trust, and polish pass

Product-side criteria are about accuracy, reassurance, and reliability. Walk through as a first-time user:

- [ ]  Obvious what to do on every screen; empty states are helpful
- [ ]  After approving, success is unmistakable — amount, category, and the **new remaining budget** restated
- [ ]  Amounts are formatted consistently (¥12,000, not 12000) everywhere, including error messages
- [ ]  Error messages are actionable human language, not `Validation failed: Amount exceeds budget` — say how much is actually left
- [ ]  Remaining budget is visible *at the moment of decision*, not one click away
- [ ]  Current state of every request visible at a glance, for both member and approver
- [ ]  Destructive actions confirmed before they happen
- [ ]  Works on a phone-sized screen
- [ ]  Consistent language, consistent date formatting, no leftover scaffold styling

## Phase 10 — Presentation preparation

Structure the talk around **decisions, not a feature tour**. A screen demo is what everyone does; explaining tradeoffs is what differentiates.

| # | Section | Time | Content |
| --- | --- | --- | --- |
| 1 | Problem & users | 1 min | Who has what pain, what value you deliver |
| 2 | Live demo of core loop | 3–4 min | Draft → submit → approve with remaining budget updating, then a deliberate approval that gets blocked by the cap |
| 3 | Design | 3–4 min | ER diagram, budget-vs-expense split, state machine, invariant→app→DB table |
| 4 | The hard problem | 2 min | Concurrent approval against a budget cap: the race, why a unique index cannot express it, row lock vs. counter + check constraint, and the tradeoff you accepted |
| 5 | Testing strategy | 1–2 min | The risks you chose and why |
| 6 | Extras | 1–2 min | User problem → feature → why prioritized; plus what you chose not to build |
| 7 | AI usage | 1 min | Where it helped, and one concrete case where you overrode it |
| 8 | What I'd do next | 30 s | Known limitations, honestly stated |
- Rehearse the demo; have a backup video and screenshots in case the deploy misbehaves.
- Practice out loud with a timer. Running over time reads as poor scoping.

## Phase 11 — Q&A and live-exploration readiness

The most under-prepared phase. You may be asked to **investigate a bug or make a small change on the spot**.

### Question bank — rehearse aloud

- Why this data model? What would you change if X?
- Walk me through what happens, line by line, when an approver clicks 承認.
- What happens if two approvers approve at the same moment against the same budget? **Prove it.**
- Is the approved used amount stored or derived? Why? What breaks with the other choice?
- Why integer yen and not decimal?
- Which month does an expense count toward, and where in the code is that decided?
- Where is authorization enforced? Show me the code.
- Why not just validate in the model?
- Which test would fail first if I broke this rule?
- What stops a member approving their own expense?
- What is the worst bug still in here?
- How would this behave with 10,000 expenses across three years of budgets?
- What did AI write, and how did you verify it?
- If you had one more week, what would you do?

### Practical readiness

- [ ]  Navigate your own codebase instantly — know the file for every feature. Fumbling in your own repo is a bad signal.
- [ ]  App running locally, tests green, and you know how to run a single test fast
- [ ]  `git log` clean; able to point at specific commits
- [ ]  **Rehearse a live change:** have someone request a field or rule tweak, and do it in 10 minutes with a test. Practice the motion: reproduce → locate → test-first → fix → verify.

<aside>
🗣️

**Answering "I don't know":** say *"I don't know — my hypothesis is X, and I would verify it by Y."* That is a strong answer. Bluffing is fatal.

Never say "AI generated that part" as an explanation. Using AI is not penalized; not understanding the output is.

## The through-line

Three habits, maintained from day one, cover most of the rubric.

1. **`DECISIONS.md` updated the moment you decide anything** → covers "explain your design judgments," feeds the presentation, answers Q&A.
2. **Every business rule enforced at two layers, and tested** → covers integrity, boundary conditions, and testing criteria at once.
3. **Ship a vertical slice early, freeze features early, polish late** → covers scoping judgment, UX, reproducibility, and deployment — the things that silently sink projects in the final week.
